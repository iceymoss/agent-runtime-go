description: 生成功能需求规范文档。当用户想开发新功能、需要 spec、需求分析、功能规划时触发。这是所有开发工作的起点。
---

生成功能需求规范文档。本项目是库，spec 的重心是**公开 API 契约与语义边界**，不是页面和接口。

## 输入

用户用一句话描述想做什么（可以很粗糙）。

## 步骤

### 1. 需求访谈（必须做）

用 AskUserQuestion 逐个确认：

- **能力定位**：这个能力属于根包内核、某个现有子包、新子包、`providers/`、还是只属于 `demo/icoder`？
- **调用方故事**：谁在什么场景下用它，期望什么结果？
- **公开 API 形状**：新增/修改哪些导出符号？能不能用现有类型表达？
- **语义边界**：什么算成功、什么算可恢复错误（`ToolResult{IsError:true}`）、什么算终止错误、什么算挂起
- **异常场景**：上游失败、取消、超时、重复执行、并发、进程崩溃后恢复
- **兼容性**：是否破坏已发布的导出面或持久化值（`StopReason` / `Outcome` / `RunStatus` 等常量字符串）
- **边界**：明确不做什么（尤其"不放进库里"的部分）
- **优先级**：MVP 包含哪些？哪些后续迭代？

每个问题等用户回答后再问下一个。"不确定"的标注为待定。

### 2. 代码调研（自动执行）

用 subagent 调研，不要让用户操心：
- 已有的相似能力实现模式（同类子包的 `contracts.go` / `memory.go`）
- 相关的根包类型与哨兵错误，能否复用
- 依赖方向是否可行（是否会违反 `deps_test.go` 的三条铁律）
- 需要同步更新的文档页与测试

### 3. 生成 Spec

写入 `docs/specs/{功能名}.md`（该目录当前不存在，首次创建即可；它是内部工作文档，不进 VitePress 站点导航）：

```markdown
# {功能名}

## 状态
- 创建日期: {日期}
- 状态: 草稿

## 目标
（一句话说明要解决什么问题）

## 非目标
- （明确不放进库、留给调用方的部分）

## 调用方故事
作为 {调用方角色}，我想要 {能力}，以便 {价值}

## 归属
- 包: 根包 agent / 子包 <name> / providers/<name> / demo/icoder
- 理由: （为什么不放在别处）

## 公开 API

### 新增/变更的导出符号
| 符号 | 类型 | 说明 |

### 兼容性影响
- BREAKING: （有则列出，并写明迁移方式）
- 复用的现有类型/错误: （避免重复概念）

## 语义

### 正常流程
1. ...

### 异常与终态
| 场景 | 处理方式 | Outcome / StopReason / 错误 |

### 并发与恢复
- 并发安全假设:
- 崩溃恢复行为:（涉及 Checkpoint/RunSnapshot 时必填）

## 实现步骤（每步可独立 commit）
1. [ ] 契约与类型（contracts.go / 根包类型）
2. [ ] 校验与错误（validation.go / errors.go）
3. [ ] 内存参考实现（memory.go）
4. [ ] 外部包测试（package <name>_test）
5. [ ] 中英双语文档 + README + CHANGELOG Unreleased
6. [ ] （可选）demo/icoder 接入验证

## 参考的现有模式
- {文件路径} — 参考了什么

## 测试计划
- [ ] 正常路径
- [ ] 非法输入与错误路径
- [ ] 并发 / -race
- [ ] （适配器）agenttest.TestModel（工具）agenttest.TestTool

## 待定事项
- ...

## MVP 范围
```

### 4. 让用户审阅

生成后告诉用户：
- 请审阅 `docs/specs/{功能名}.md`
- 重点确认：能力归属、公开 API 形状、兼容性影响、MVP 范围
- 确认后用 `/tdd` 逐步开发
